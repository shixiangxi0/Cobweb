# 如何理解双世界设计

这篇文档旨在提供一个"架构参考文档"，帮助熟悉现代软件工程的开发者，建立对双世界架构的直觉。

---

## 1. 事件与状态：Event Sourcing 与 CQRS 的游戏化映射

传统游戏引擎大多是"状态驱动（State-Driven）"的，将内存中的变量视为世界的真理。而在双世界设计中，**"事件才是事实，状态只是投影"**。

这在严肃软件工程中对应着 **事件溯源（Event Sourcing）** 与 **命令查询职责分离（CQRS）**：
* **逻辑事件（Event / Write Model）**：玩家按下的按键、碰撞触发的伤害，它们是系统绝对不可变的"事件事实"。逻辑引擎是一条绝对串行的处理管线，通过单向规约（Reduce）这些事件来计算和累加核心状态。
* **视觉效果（Projection / Read Model）**：表现层的动画、特效、粒子，本质上是引擎根据事件流派生出的"读取/投影模型"。它们被分离在另一条主轴上，专门用于优化人类的连续视听反馈，由于只是投影，它们天然可以被随时擦除和基于事件重新演算。

---

## 2. 状态分层：借用检查（Borrow Checker）与作用域

双世界设计的状态分层，在结构上与 Rust 的所有权模型高度同构：

* **持久状态（唯一可变借用 `&mut T`）**
核心状态树在任何时刻只有逻辑层持有写权限，所有状态演进严格串行。这不是约定，是结构约束——竞态在架构层面无法发生，原因和 Rust 不允许同时存在两个 `&mut T` 完全相同。

* **逻辑层（`&mut T` 的作用域）**
持久状态将权力委托给当前场景，场景内所有状态推演在逻辑层发生。场景结束时，权力收回，局部状态整体销毁——和 Rust 变量离开作用域自动 Drop 的机制完全对应。

* **表现层（不可变借用 `&T`）**
渲染组件只持有逻辑快照的读权限。动画播放多长、被强行中断、甚至整个渲染层崩溃，都不会反向影响逻辑状态。多个渲染组件可以同时读同一份快照，和 Rust 允许同时存在多个 `&T` 的理由一样：只读不会产生竞争。

* **临时状态（生命周期 `'a`）**
逻辑层为了处理连续状态（如格挡帧、连击窗口），在内部创建的临时状态。它的生命周期由创建它的上层逻辑作用域严格管理：窗口关闭或被抢占时，scope 直接销毁，内部过程状态自然消亡，不需要手动清理，不会有残留。

## 3. 渲染自治：单向数据流与 UI 局部状态

"渲染组件持有表现，但不持有逻辑"，这句话听起来像是悖论：如果怪物组件能自己判断距离并跑向玩家，它怎么可能没有业务逻辑？

为了理解这种隔离的精妙，可以带入 **现代前端的组件分治设计（如 React + Redux/Flux 范式）**：

* **表现组件的 Local State（局部模拟自治）**：
  在前端架构中，我们绝不会把"下拉框展开动画的中间值"、"按钮的 Hover 渐变"放入全应用级别的 Redux Store。同理，渲染组件完全可以内部维护高度复杂的物理位移模拟、寻路插值（这是它的 Local UI State），以保证画面的响应率。但这些运算被严格限制在视觉表现圈层，不作为世界的真理。
* **核心校验的 Global Store（单向数据流）**：
  不管渲染组件内部独立演算了什么，只要不向上抛出（Dispatch）关键事件，它就不会影响业务的状态走向。只有当渲染组件检测并确认了实质性的接触，它才会向逻辑层发射一个离散的安全载荷（Event Payload）。

这种分治将高频、连续、充满噪音的"感知模拟"隔绝在了外围，确保了核心引擎（Reducer）的纯粹性与推演的绝对确定性。

> ⚠️ 一般来说，初次认识双世界架构的开发者，往往会将玩家输入都当作从表现层到逻辑层的处理，这是错误的，你必须在设计阶段就将每个玩家的输入映射到相关联的状态分层上，归渲染组件，默认自治，可丢弃。影响但只在当前场景内有效的，归逻辑层，随场景生灭。影响跨场景推演的，归持久状态，必须存档。

---

## 结语

双世界设计将这些已在其他现代领域被反复验证的工程范式（所有权控制、单向数据流、事件溯源）系统化地编织在了一起，化作一把切分游戏架构职责的**奥卡姆剃刀**。

它为饱受网状结构、回调灾难与状态耦合之苦的游戏开发，提供了一套具有高度工程美学的心智模型。
